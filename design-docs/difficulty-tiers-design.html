Within-topic difficulty tiers

Every procedural maths generator can now ease off or push harder inside the same topic, driven by rolling accuracy — instead of a fixed spread of numbers that never noticed whether a child was struggling or bored.

150 / 150 tests passing ~70 question styles tiered 0 regressions in STANDARD tier

How a tier gets chosen

One rule, one place it lives — every call site asks the same function rather than re-deriving a threshold.

Reading left to right: a topic's recent accuracy decides a tier once per question, that tier rides through generate() down to whichever style builds the question, and each style's own byTier() call is the only place a range actually changes.

The three tiers

Same question shape, same correct formula — only the magnitude of the random inputs moves.

Easy · Learning
"Find 10% of 120."
Standard · Practising
"Find 15% of 260."
Hard · Secure
"Find 65% of 1,080."

How it shipped

Four phases, each verified against the full test suite before moving on — the standing rule for this codebase after the correctness audit that preceded this work.

01
Shipped

Infrastructure

  • src/engine/difficulty.js — TIER, tierFromMastery(), byTier(). One mapping from mastery status to tier, reusing statusOf() rather than re-deriving accuracy thresholds.
  • topic.js's makeTopic() now calls style.build(rng, tier) instead of style.build(rng), defaulting to STANDARD.
  • index.js's generate() and session.js's buildRound() thread a tier through, computed from the mastery of whichever topic is actually pinned.
Weighed and rejected: a per-question difficulty slider in the UI. Rejected — the app already has one lever (accuracy) that means the same thing to a child as it does to the engine; a second, manual one would just be more to configure for no teaching benefit.
02
Shipped

The six hand-rolled maths topics

  • Place value, factors, percentages, algebra, measure, angles — the oldest generators in the app, each an internal rng.int(0,N) switch rather than the newer style-list shape.
  • Every numeric range rewritten as byTier(tier, easy, standard, hard), with standard pinned to the exact original bounds.
  • One correctness rule enforced throughout: never pass an rng.int() call as a byTier argument — byTier's arguments evaluate eagerly, so a live-called argument would silently consume randomness even on the branch not taken, desyncing every seeded test.
Brainstormed per style: for the angle-classification style, HARD weights toward the obtuse/reflex boundary — the genuinely harder judgement call — rather than just picking bigger numbers, which would have made no conceptual difference to that particular question.
03
Shipped

The 16 style-list topics

  • 8 topics in topics-varied.js (order of operations, negatives, time & speed, averages, ratio, fractions, decimals, multi-step problems) and 8 multi-step challenges in challenges.js — around 55 more question styles.
  • Challenges got the most conservative tiering of all three phases: several back-compute one value from the others specifically to guarantee a clean division (no stray pennies), so ranges were widened without disturbing that structure, verified by hand against the guard clauses already in the file.
Brainstormed: whether HARD-tier bar-model visuals (one segment drawn per unit) could render an unreadable wall of segments — the exact bug class caught in the prior correctness audit. Kept every HARD range for a per-unit visual under the same ceiling already used elsewhere in the codebase.
04
Shipped

Verify, test, ship

  • 3,600 generated questions across every topic × style × tier, zero crashes, zero malformed questions.
  • tests/difficulty.test.js added: tier-from-mastery mapping, a magnitude check (HARD > EASY on average), and a full sweep confirming every topic still produces a valid question at every tier.
  • Full suite run after every phase — 150/150 passing, up from 141 before this work (9 new tests, 0 removed).
Found along the way: a real, pre-existing bug unrelated to tiering — a round pinned to a topic with no declared styleIds (all six Phase 02 topics, plus every book-style me1–me16 bank) silently ignored the pin and served random-subject questions instead. Fixed in session.js, covered by a regression test, since it sat directly in the code this work was already touching.

The one invariant that made this safe

Every byTier call in the codebase follows this exact shape. The middle argument is never touched.

// easy · standard · hard — standard is the ORIGINAL range, unchanged
const [lo, hi] = byTier(tier, [5, 10, 20, 25, 50], [5, 10, 15, 20, 25, 30, 40, 50, 60, 75], [55, 65, 70, 80, 85, 90, 95]);
const pct = rng.pick(pctPool);

// NEVER: rng.int()/rng.pick() as a byTier argument — evaluated eagerly,
// consumes randomness on the branch not taken, desyncs every seeded test.
